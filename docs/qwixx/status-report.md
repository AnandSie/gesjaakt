# Qwixx Implementation — Status Report

_Branch: `feature/qwixx` · Written to checkpoint context before continuing in a fresh session._

## Goal

Add Qwixx as a third game in this hackathon engine, using a spec-driven / TDD workflow instead of hand-coding it directly like Gesjaakt and Take-5!:

1. Capture the rules as a numbered, verified markdown spec (`docs/qwixx/rules.md`, IDs `QX-001`...`QX-033`).
2. Write unit tests first, each referencing the rule ID(s) it covers, against a thin API-shape stub (`throw new NotImplementedException()` everywhere).
3. Implement the actual logic afterward, by hand, using the red tests as the spec to satisfy.

All three steps are now done for every class, including `QwixxGameDealer.Play()` — the whole Qwixx test suite is green.

## Key design decisions made along the way

- **Player delegates to a Thinker, same as the other two games.** Caught mid-build: my first `QwixxPlayer` draft was just a scoresheet with no way for a bot to act — missing the actual point of the hackathon. Fixed by adding `IQwixxThinker` (`DecideWhiteMark`, `DecideColoredMark`, `DecideToLock`) and making `Player` a pure delegator, matching `GesjaaktPlayer`/`TakeFivePlayer`.
- **Two decision points, not one**, because a Qwixx turn isn't symmetric: `DecideWhiteMark` is offered to *every* player every turn; `DecideColoredMark` only to the active roller. A third, `DecideToLock`, was added later (see below).
- **Locking is a real choice, not automatic.** Re-reading `QX-023` ("...or simply choose not to lock") while comparing `Player` against the other games surfaced that neither decision method asked "do you also want to lock?" — `IQwixxThinker.DecideToLock` closes that gap.
- **`Row.IsLocked` is derived, not stored.** A row has 11 numbers + 1 lock cell = 12 max marks; 12 is only reachable by having also marked the lock. So `IsLocked == (MarkedCount == 12)` — no separate flag that could drift from the mark count.
- **Locking is global game state, not per-row.** `GameState.IsColorLocked(color)` is a separate, genuinely independent fact from any single player's `Row.IsLocked` — "did I lock my row" (scoring-relevant, per player) vs. "is this color dead for everyone" (table-wide). Keeping the two in sync is explicitly **left as the dealer's job**, deferred on purpose (see Open Items).
- **Read-only views expose queries, never mutable objects.** `IQwixxReadOnlyPlayer` exposes `MarkedCount`/`IsRowLocked`/`CanMark` as methods, never the mutable `QwixxRow` itself — so a bot's `Decide()` can't reach in and mutate a row directly, mirroring why `IReadOnlyDeck` exists.
- **Test data should be literal, not re-derived.** Caught and fixed once already: shared test helpers that "compute" ascending/descending sequences from a color were removed in favor of explicit literal numbers per test case, because a bug in that shared helper would have silently validated against itself instead of catching anything.
- **`Play()` runs whole rounds, checking `IsGameOver` only between them**, not after every individual turn — this directly implements `QX-027` (finish the current round before stopping) without extra bookkeeping: the loop is `while (!IsGameOver) { for each player: PlayTurn(); NextPlayer(); }`.
- **`GameDealer.TryMark` is the single place that keeps `Row.IsLocked` and `GameState.IsColorLocked` in sync** — every mark attempt goes through it, and it calls `GameState.LockColor(color)` right after a successful `Row.Lock()`. This resolved the sync concern raised as an open item earlier, without needing the atomic `TryLockRow` alternative that was considered.
- **A thinker's colored-mark choice is validated against the roll's actual candidate sums**, not just against `Row.CanMark`. `IQwixxThinker` implementations are hackathon-participant code — an untrusted boundary — and `Row.CanMark` alone can't detect a fabricated number (e.g. claiming a sum the dice never produced) since it only checks ordering/lock state. `QwixxDiceRoll.ColoredSums(color)` already computes the exact legal set, so `OfferColoredMark` checks membership before marking.
- **`OfferWhiteMarkToAllPlayers` uses a single loop over all players, calling the single-player `OfferWhiteMark` exactly once per player.** An earlier version conflated "did this mark succeed" with "is this the active player" in one `&&`-joined `if`; a later attempt to fix that split the active player out into a separate call site entirely, which then had two places calling `OfferWhiteMark`. Settled on: one loop, one call site, and the active player's outcome is just recorded via a plain identity check inside that same loop — natural player-list order is preserved, and no marking logic is duplicated or reordered.
- **`OfferWhiteMarkToAllPlayers`/`OfferWhiteMark`/`OfferColoredMark` are all `void`.** House naming convention: a verb-named method (`Offer...`) is fire-and-forget, a noun-named one is a getter. `TryMark` keeps its `bool` return despite being a verb, since the `Try...` prefix is an established .NET idiom (`TryParse`-style) distinct from a plain fire-and-forget verb. The `QX-013` penalty check needed to know "did the active player mark *anything* this turn," which is answered by `GetMarkedCount(player)` — a plain total across all 4 rows, called before and after both offer steps — kept outside the offer methods entirely rather than threaded through their return values.
- **Dice rolling was extracted from `QwixxGameDealer` into `QwixxDiceRoller`/`IQwixxDiceRoller`**, injected via the dealer's constructor, with `QwixxRules.MinDieValue`/`MaxDieValue` replacing the `1`/`7` magic numbers that were passed to `Random.Next`. This both gives the roller its own focused test coverage and resolves the "can't seed/replay `Play()`'s dice sequence in a test" gap noted below (the dealer can now be constructed with a fake `IQwixxDiceRoller` in a test, though no test yet exploits this for deterministic `Play()` coverage).
- **A single die's randomness was pulled one level further out, into a generic `Dice` class in `Domain.Entities.Components`** — game-agnostic, not under the `Qwixx` namespace, not referencing `QwixxRules` at all. `Dice(int min, int max)` takes its range from the caller, exactly like `Deck<TCard>(int min, int max, ...)` already does — `QwixxDiceRoller` now just constructs `new Dice(QwixxRules.MinDieValue, QwixxRules.MaxDieValue)` and calls `.Roll()` six times, the same way `TakeFiveDeckFactory` builds its `Deck` from `TakeFiveRules.MinCardValue`/`MaxCardValue`. Reusable by any future game without modification.
- **Player-count validation (QX-006) lives at the top of `Play()`, not in the constructor.** The originally-flagged open item said "constructor validation," but the constructor only takes `IQwixxGameState`/`IQwixxDiceRoller` — players are added afterward via `Add()`, possibly across multiple calls, so the minimum can't be meaningfully checked until the game is actually about to start. Throws `InvalidOperationException` if `Players.Count()` is outside `QwixxRules.MinNumberOfPlayers`/`MaxNumberOfPlayers`.
- **Adding that validation required reworking the `QwixxGameDealerTests` single-player test setups**, since 10 of them used exactly 1 player (below the new minimum of 2) to keep each test focused on one behavior. Fixed by having `SetupExactlyOneRound` auto-pad with an inert (always-declining) second player when fewer than the minimum are given, *and* rotating `PlayerOnTurn` so the real player under test is only ever active for the round's first turn — this preserves every existing test's single-turn assertions unchanged (traced through each one by hand: marking/locking/rejection tests are naturally idempotent against a same-state repeat, but the two penalty tests specifically needed the inert player to "absorb" the round's extra turn, or they'd have double-counted `AddPenalty`).
- **`IQwixxThinker` now extends `IStatefull<IQwixxReadOnlyPlayer>` (2026-07-25), superseding the "no base class"/"no built-in way to know who am I" decisions below.** Directly requested: mirror `ITakeFiveThinker`'s `SetState`-based pattern instead of the `gameState.Players.Single(p => p.Name == Name)` self-lookup hack `GreedyQwixxThinker`/`ManualQwixxThinker` were using. `QwixxPlayer.DecideWhiteMark`/`DecideColoredMark`/`DecideToLock` each call `_thinker.SetState(AsReadOnly())` immediately before delegating, so the thinker's own state is always current *at the moment of that specific decision* (not just once per turn) — necessary because a player's own row state can change between, say, the white-mark step and the colored-mark step in the same turn. Added test-first: 3 new `QwixxPlayerTests` assert `SetState` was called with a read-only view whose `MarkedCount` reflects a mark made just before the call, confirmed red (missing behavior) before implementing.
- **`BaseQwixxThinker` was introduced in `Application.Qwixx.Thinkers`**, implementing `SetState` to store the pushed state in a protected `Me` property, mirroring `BaseTakeFiveThinker`/`_hand`. `TemplateQwixxThinker`/`GreedyQwixxThinker`/`ManualQwixxThinker` all now extend it instead of implementing `IQwixxThinker` directly — this reverses the earlier "matches Gesjaakt's simpler no-base-class pattern" decision now that there's a concrete need (and reason) for one. `GreedyQwixxThinker`/`ManualQwixxThinker` no longer need the `Name`-lookup self-identification hack at all; they just read `Me` directly.
- **No `QwixxGameEventCollector`/`IQwixxGameEventCollector` was created**, unlike Gesjaakt/Take-5! each having one — `QwixxGameDealer`/`QwixxGameState`/`QwixxPlayer` raise no C# events at all (the deliberately-skipped "console/UI events" item), so there is nothing for a collector to attach to. `QwixxGame.PlayWith()` simply doesn't call `.Attach(...)`, unlike `GesjaaktGame`/`TakeFiveGame`.
- **`GreedyQwixxThinker`/`ManualQwixxThinker` were both necessary, not optional** — `TemplateQwixxThinker` throws `NotImplementedException` everywhere by design, so `QwixxPlayerFactory.Create()` needed at least one genuinely working bot to populate a default simulated game, and `CreateManualPlayer()` needed a human-playable thinker, mirroring how Gesjaakt/Take-5! each have a "greedy"-style default plus a manual thinker.
- **`QwixxRow` gained `IsMarked(int)` (2026-07-25) specifically to support a real score-sheet render.** Before this, `QwixxRow`/`IQwixxReadOnlyPlayer` only tracked *counts* (`MarkedCount`, last-marked number) — enough to enforce rules, but not enough to say *which* of the 11 numbers in a row were actually crossed out vs. merely skipped over (QX-017), which is exactly the distinction a human player needs to see on their own sheet. Added test-first (4 new `QwixxRowTests`), backed by a `HashSet<int>` populated in `Mark()`. Combined with the pre-existing `CanMark`, this gives three renderable states per number: marked (`IsMarked` true), available (`IsMarked` false, `CanMark` true), permanently skipped (both false) — no new method needed for the third state, it falls out of the other two.
- **`ManualQwixxThinker`'s score sheet is written via raw `Console.WriteLine`, not through `IPlayerInputProvider`'s logger-based prompt text.** Discovered by direct experiment (see Problems found and corrected): `ILogger.LogCritical` — which is how `CLIPlayerInputProvider` displays every "question" string — silently strips ANSI escape codes from message content, while `Console.WriteLine` passes them through untouched. So the colored score sheet (and the colored candidate list in `DecideColoredMark`) print directly via `Console.WriteLine` *before* the actual input prompt, and only the plain-text prompt itself goes through `playerInputProvider.GetPlayerInputAsInt(...)` as before — this keeps the shared `IPlayerInputProvider`/logging infrastructure completely untouched, scoping the whole fix to `ManualQwixxThinker`.
- **All white-mark/colored-mark options shown to a human are now filtered through a `CanReallyMark(gameState, color, number)` helper before being listed (2026-07-25).** Bug report: after marking Red via the white sum, the colored-mark menu still offered an option that couldn't actually be picked — nothing visibly wrong, but selecting it silently did nothing, since `QwixxGameDealer.TryMark` just rejects an invalid mark with no feedback back to the thinker. Root cause: the option/candidate lists were built purely from dice math (`Enum.GetValues<QwixxColor>()`, `roll.ColoredSums(color)`), never checked against whether the mark would actually be accepted. `CanReallyMark` mirrors exactly what `TryMark` checks (`!gameState.IsColorLocked(color) && Me.CanMark(color, number)`) and is now applied in three places: the white-mark options, the colored-mark candidates (also `.Distinct()`-ed, since a double white roll can legitimately produce the same candidate sum twice per QX-010, which would otherwise list as two identical-looking choices), and — a related gap found while fixing this — the score-sheet cell coloring itself, which previously only checked `Me.CanMark` and so showed a row locked *by another player* as still "available" (since only the locking player's own `QwixxRow.Lock()` ever gets called; a non-locking player's row never learns about the lock except via the global `gameState.IsColorLocked`). Verified via a bounded, output-capped console run: the "or N to skip" number now visibly shrinks turn over turn as rows fill up, and cross-checked that a fully-untouched row's numbers are exactly the ones still offered as menu candidates.
- **Score-sheet rendering moved out of `ManualQwixxThinker` into a shared `QwixxScoreSheetExtensions` class (2026-07-25), on request ("all the logging to terminal is done using ToString methods similarly to the other two games").** Not a literal `ToString()` override — mirrors `TakeFiveCardExtensions.ToTableString()` instead, which is the closer precedent: a *composite* render that needs more than one object's own state (`TakeFiveReadOnlyGameState.ToString()` delegates to `CardRows.ToTableString()` for exactly this reason). `IQwixxReadOnlyPlayer.ToScoreSheetString(gameState)` needs both the player's own view *and* the surrounding `IQwixxReadOnlyGameState` (for the "locked by another player" distinction), and `IQwixxReadOnlyPlayer` deliberately never exposes the underlying mutable `QwixxRow` a plain per-object `ToString()` override would otherwise want to delegate to. `ManualQwixxThinker` now just calls `Me.ToScoreSheetString(gameState)` and `Me.CanReallyMark(...)`, with all the `Render*` helpers and ANSI constants gone from the thinker itself.
- **`QwixxScoreSheetExtensions` was first placed in `Domain.Extensions` (matching `TakeFiveCardExtensions`'s literal location), then moved to `Application.Qwixx` on request.** The first placement was a conscious, flagged trade-off (ANSI codes in the domain layer, justified only by "keeping the colors mattered more than architectural purity"); moving it to `Application` resolves that cleanly — the domain stays entirely presentation-free, `TakeFiveCardExtensions` (plain text) is the one case of formatting-in-`Domain.Extensions` for this codebase, and Qwixx's colored version lives with everything else terminal-specific (`ManualQwixxThinker`, `CLIPlayerInputProvider`). No functional change from the move — re-verified end-to-end (bounded/output-capped console run) that the render is byte-for-byte identical to before.
- **Thinker exceptions are caught in `QwixxPlayer`, not in `QwixxGameDealer` (2026-07-26).** The two existing games disagree on where this belongs: `TakeFivePlayer.Decide` wraps its own thinker calls, while `GesjaaktGameDealer.PlayerChoice` wraps them in the dealer — and Gesjaakt's own code carries a `// REFACTOR - move try catch inside player` comment saying the player is the right home. Qwixx follows that stated preference. `QwixxPlayer` gained `event EventHandler<ErrorEvent>? DecideError` (mirroring `ITakeFivePlayer`) and a private `DecisionOrFallback<TDecision>` helper that wraps all three `Decide*` delegations, rather than three near-identical try/catch blocks. Named as a noun, not a verb, per the house convention that verb-named methods are fire-and-forget. `SetState` is inside the try too, since a participant may implement `IQwixxThinker` directly instead of extending `BaseQwixxThinker`.
- **Every fallback is the "do nothing" answer**: decline the white mark, decline the colored mark, leave the row unlocked. Each is a legal Qwixx move, so a broken thinker degrades into a passive player instead of corrupting the game — and critically, `DecideToLock` fails *closed*: locking is irreversible and closes the color for every player (QX-024/QX-025), so it must never happen on behalf of a thinker that couldn't answer. The active player still risks the QX-013 penalty for marking nothing, which is the fair consequence rather than something to paper over.
- **Three dealer events, chosen to match what the status report already identified as notable**: `ColorLocked` (`WarningEvent`, QX-024/QX-025), `PenaltyTaken` (`WarningEvent`, QX-013/QX-014) and `MarkRejected` (`ErrorEvent`). The levels are not arbitrary — `App.SelectGameMode` sets the minimum event level to `Error` for simulations and `Info` for manual games, so the two per-turn `Warning` events stay out of a 1000-game simulation's output while still showing during a manual game, exactly as Gesjaakt's `PlayerGesjaakt` warning does. `MarkRejected` is `Error` because it can only fire when a thinker asks for something the rules forbid; it fires from all three rejection paths in the dealer (locked color, row ordering, and a fabricated candidate sum), which were previously all silent returns — the same silence that made the unmarkable-menu-option bug so hard to diagnose.
- **No `DiceRolled` event**, despite it being the obvious fourth candidate: rendering the roll would mean exposing the four colored die values on `QwixxDiceRoll`, which currently keeps them private behind `ColoredSums(color)`. Not worth widening that API for a log line.
- **`IQwixxGameEventCollector` has no `Attach(IQwixxGameState)` overload**, unlike both existing collectors. `QwixxGameState` genuinely raises no events — every notable moment is decided by the dealer or reported by the player — so the overload would have nothing to subscribe to. This finally makes the "no collector exists" note obsolete: `QwixxGame` now takes an `IQwixxGameEventCollector` and chains `Attach(dealer).Attach(players)`, and `AddQwixxGame()` registers it alongside the other two games' collectors.
- **`Application.Qwixx` tests live in `DomainTests`, under `ApplicationTests/Qwixx/` (2026-07-26)** — not in a new test project. `DomainTests.csproj` already references `Application.csproj`, and `Players/PlayerTests.cs` already tests `Application.Gesjaakt.Thinkers` types, so this follows existing precedent instead of adding a project (and its solution wiring) for one folder. The folder is named `ApplicationTests`, **not** `Application`, on purpose: a `DomainTests.Application.Qwixx` namespace would shadow the real `Application` root namespace, silently binding `using Application.Qwixx;` to the test namespace instead of the production one.
- **`QwixxGameTests` doubles as the missing integration test.** Broader observation #6 asked for "one lightweight integration test per game… assert it doesn't throw"; `PlayWith_PlaysAGameThroughToItsEndCondition` goes further and asserts the game actually reached a QX-026 end condition (two locked colors, or a player at the penalty limit), which a game that silently did nothing would fail. `PlayWith_StartsAFreshGameEachTime` compares by *reference* on purpose — both rosters carry the same names, so `BeEquivalentTo` would pass even if the previous game's players came back.

## Problems found and corrected

1. **Initial rules.md draft was wrong** on the locking mechanic (thought the 2nd-to-last number needed 5 marks; actually only the *lock cell* does, the last number itself has no special gate) and on dice combinations (said 4 candidate sums, actually 8 — 2 white dice × 4 colors). Both corrected after your review against the physical rules, logged in the rules.md "Verification log".
2. **`CanLock` tests only covered one direction.** First pass tested ascending (Red) only; descending rows (Green/Blue) reach their "last number" via a different sequence, so this was a real gap, not just missing coverage — fixed with literal per-color `DataRow` data.
3. **Missing Thinker/Decide architecture in `QwixxPlayer`**, and **missing `DecideToLock`** — both described above.
4. **`QX-012` was fabricated during initial drafting and was wrong.** It claimed a player may mark at most one number per row per turn. The real rulebook (re-checked directly, 2026-07-23, prompted by a question about whether the active player can really use both dice actions) has no such restriction — the white-sum step and the active player's colored-combo step are each independently limited to one row per action, but nothing stops both from targeting the *same* row in one turn (a known legitimate tactic: e.g. white sum marks red 5, colored combo marks red 8 in the same turn). `rules.md` QX-012 was corrected in place (see its Verification log), and `QwixxGameDealer` had a same-row exclusion check built specifically to enforce the wrong rule — removed along with the per-color tracking machinery (`GetMarkedCountsByColor`/`ColorWithMarkedCountAbove`) that existed only to support it, which also substantially simplified `PlayTurn`. Verified via a deterministic smoke test (fixed dice roll, single player) that a mark via white *and* a mark via colored now both land in the same row in one turn as expected.
5. **First draft of `Play()`'s multi-player unit tests had a wrong mental model.** Assumed "one round" meant each player gets offered the white mark exactly once; actually a round is `Players.Count()` turns, and the white mark is offered to *every* player on *every* one of those turns (real Qwixx behavior — everyone reacts to every roll, not just once per round). 3 tests initially asserted `Times.Once` where the real count was `Times.Exactly(playerCount)`; fixed by correcting the expected counts and, for the round-completion test, using `SetupSequence` on `PlayerOnTurn` so each of 3 players is genuinely active for exactly one of the round's 3 turns.
6. **First attempt at a colored score sheet embedded ANSI codes directly in the string passed to `IPlayerInputProvider.GetPlayerInputAsInt`, and rendered as completely plain text — no color at all.** Confirmed the cause with an isolated throwaway console app: `ILogger.LogCritical("\x1b[91mRED\x1b[0m")` outputs `RED` with the escape bytes stripped, while `Console.WriteLine("\x1b[91mRED\x1b[0m")` outputs the bytes intact (verified via `grep`/`cat -A` on the raw output — zero ESC bytes with the logger path, present and correctly positioned with `Console.WriteLine`). Fixed by moving the score sheet (and colored candidate list) to direct `Console.WriteLine` calls, keeping the actual prompt text passed to `IPlayerInputProvider` plain.
7. **First version of the manual-game menus offered options that couldn't actually be marked, reported directly ("I decided to use red 3 via the white dice... a red 3 [sic — a colored-mark candidate] is presented as an option [again]... I cannot check it").** The white-mark and colored-mark option lists were built purely from dice math, with no check against the player's actual row state or the global lock — so a number already marked, already skipped past, or in a globally-locked row could still appear as a selectable menu choice, which then silently did nothing when picked (`QwixxGameDealer.TryMark` just rejects it, with no feedback path back to the thinker). Fixed by adding `CanReallyMark` (mirroring `TryMark`'s own checks) and filtering all three affected surfaces: white-mark options, colored-mark candidates, and the score-sheet cell coloring itself (which had the identical gap for a color locked by *another* player, since only the locking player's own row ever gets `Row.Lock()` called).

8. **`QwixxPlayer` had no `ToString()` override — fixed 2026-07-26.** Spotted in a real console run: the end-of-game results block printed `- Domain.Entities.Game.Qwixx.QwixxPlayer` per player, where `GesjaaktPlayer`/`TakeFivePlayer` print a readable self-description. Now renders `Alice, has 22 points, marks [Red 1, Yellow 4, Green 3, Blue 4] and 1 penalties`, following `GesjaaktPlayer.ToString()`'s shape. Deliberately plain text and in `Domain`, per the principle in broader-observation #8: this string ends up in logs, exception messages and debugger windows, so it must stay readable outside a terminal — the ANSI card-style render stays in `Application.Qwixx.QwixxScoreSheetExtensions`.
9. **New event tests repeated the exact mistake logged as #5 above.** Four of the first-draft `QwixxGameDealerTests` event tests asserted `ContainSingle()` on the captured messages and failed: `SetupExactlyOneRound` pads a single-player test up to the 2-player minimum, so a round is 2 turns and the white mark is offered to the player under test on *both* of them — a doomed Red choice is therefore rejected twice, and the inert padding player takes its own penalty on the turn it is active. Fixed by asserting against the messages naming the player under test (`ContainSingle(m => m.Contains("Unlucky"))`, `NotContain(...)`) or against the whole set's shape (`NotBeEmpty().And.OnlyContain(...)`) rather than a raw count, with a comment on each so the next reader doesn't re-derive it.

## Broader Application/Presentation layer observations (not Qwixx-specific)

Noticed while wiring `Application.Qwixx` and running the console app — these apply to the engine generally, not just Qwixx. Recorded here (2026-07-24, #7 added 2026-07-25, #8–#10 added 2026-07-26) so they aren't lost; #5 and #10 have since been fixed (on request), #8 was investigated and closed as a non-issue, the rest are unactioned.

1. **`GameRunner.RunGameWith`/`ReportSimulationResults` miscounts games when ties happen — confirmed with real output.** Every player tied for the top score gets counted as a separate "win" (`playerResults.Where(p => p.Score == winner.Score).ToList()` in `GameRunner.cs`), and `ReportSimulationResults` uses the *sum of win-counts* as both the "Total Games Played" label and the percentage denominator. A 1000-game Qwixx simulation (3 identical `GreedyQwixxThinker`s, so ties are common) printed **"Total Games Played 1030"** — 30 games had 2+ tied winners, each counted separately, so the label is a mislabel and the printed percentages are computed from an inflated denominator rather than the true game count. Pre-existing, not introduced by Qwixx, but Qwixx's tie-friendly scoring (QX-033) makes it visible in a way Gesjaakt/Take-5! probably don't hit as often.
2. **`GesjaaktGame`/`TakeFiveGame`/`QwixxGame` are near-identical copies.** `TakeFiveGame.cs` already has a `// REFACTOR - this whole class is duplicate of GesjaaktGame` comment acknowledging it; `QwixxGame.cs` is now a third copy of the same shape (build state, build dealer, add players, `Prepare()`, `Play()`, delegate `Results()`). A shared base or a small generic helper (state-factory + dealer-factory delegates) would collapse three files into one.
3. **Same duplication in `ServiceCollectionExtensions.AddXGame()` and the `*PlayerFactory` classes.** Each `AddXGame()` registers `GameRunner<T>`, `IGame<T>`, the concrete game, and the factory — `AddQwixxGame()` is a fourth copy. The factories each maintain two parallel hardcoded lists (`Create()` and `AllPlayerFactories()`) kept in sync by hand — there's already a `// REFACTOR - use DI/REFLECTION to auto create this` comment flagging this, and `QwixxPlayerFactory` hit the same "remember to add it in two places" friction.
4. **`IStatisticsCreator` is a single, non-generic, accidentally-shared registration.** Only `AddGesjaaktGame()` registers one (`GesjaaktVisualizer`); Take-5! and now Qwixx's `GameRunner<T>` both receive that *same* Gesjaakt-specific instance via DI since there's only one slot for the interface. Selecting "Visualize a thinker" while playing Qwixx would silently run Gesjaakt's visualizer against Qwixx data.
5. ~~`IQwixxThinker` has no way to know "which player am I".~~ **Fixed 2026-07-25** — `IQwixxThinker` now extends `IStatefull<IQwixxReadOnlyPlayer>`, `QwixxPlayer` pushes its own read-only view in via `SetState` before each decision, and `BaseQwixxThinker` stores it in a protected `Me` property. See the design decisions above.
6. **Zero automated coverage for the whole Application/Presentation layer.** `QwixxGame`/`QwixxPlayerFactory`/the DI wiring were verified only by manually piping stdin through `dotnet run` and reading console output (see the `Application.Qwixx` row above). One lightweight integration test per game (spin up the DI container, resolve `GameRunner<T>`, run a single simulated game, assert it doesn't throw) would catch a broken registration automatically instead of relying on someone noticing during manual testing.
7. **`CLIPlayerInputProvider.GetPlayerInputAsInt`'s retry loop has no bound or backoff on invalid input — including EOF — and can fill disk in seconds when run non-interactively (2026-07-25).** `Console.ReadLine()` returning `null` (stdin exhausted/piped input ran out) makes `int.TryParse(null, ...)` fail, which the `while (true)` loop treats as just another "invalid input" and immediately retries — with no input arriving ever again, this becomes a tight infinite loop that logs "Invalid input..." as fast as the process can spin. Hit this directly while testing manually: a `dotnet run` invocation with piped stdin that ran out mid-game produced a **6.6 GB output file in roughly 15–20 seconds** before being killed. Pre-existing, shared by all three games (any non-interactive/scripted use of `IPlayerInputProvider` is at risk, not just Qwixx) — worth a bounded retry count or explicit EOF handling.
8. **Should Gesjaakt/Take-5!'s domain-layer `ToString()`/`ToTableString()` overrides move to `Application` too, matching where `QwixxScoreSheetExtensions` ended up? Checked directly (2026-07-26) — no, not as things stand.** `GesjaaktGameState.ToString()`, `GesjaaktPlayer.ToString()`, `TakeFiveGameState.ToString()`, `TakeFivePlayer.ToString()`, `TakeFiveCard.ToString()`, and `TakeFiveCardExtensions.ToTableString()` were all grep-checked for ANSI/`ConsoleColor` codes — none exist; they're plain text throughout. That's the deciding factor, not "rendering code shouldn't live in Domain" as a blanket rule: `QwixxScoreSheetExtensions` had to move because ANSI escape codes are actively wrong outside a terminal (garbled bytes in a log file, an exception message, a debugger watch window), whereas a plain `ToString()` is a safe, universally-useful .NET convention for self-description with no such coupling. The principle worth keeping: *terminal-presentation-specific code (ANSI, box-drawing, etc.) belongs in `Application`; plain textual `ToString()` representations are fine in `Domain`.* Under that principle Gesjaakt/Take-5! are already compliant — nothing to change unless/until either grows a colored terminal experience of its own, at which point that new code should follow the same pattern Qwixx now does.
9. **Event verbosity is hardcoded per game mode — an opt-in flag would make simulations debuggable (2026-07-26, requested as a future item).** `App.SelectGameMode` fixes the minimum event level per menu choice: `Error` for a set game, `Critical` for all-combinations, `Info` for a manual game. There is no way to ask for a noisier (or quieter) run without editing that switch. Found while verifying Qwixx's new events: a 1000-game set game prints none of them, because `ColorLocked`/`PenaltyTaken` are `Warning` and the set game's floor is `Error`. That default is right — per-turn lock/penalty chatter across 1000 games is thousands of lines of noise, and Gesjaakt's `PlayerGesjaakt` warning is suppressed there for exactly the same reason — but it means *nothing* game-specific is visible when a simulation produces a surprising result, so the only way to investigate today is to recompile with a different level. **Suggested shape:** a CLI flag (there is already `--simple-console` being parsed in `Program.cs`, so the entry point for one exists) such as `--event-level=warning`, read into `SimulationConfiguration` or passed to `IGameEventHandler.SetMinLevel`, with the current per-mode values as defaults when the flag is absent. Engine-wide, not Qwixx-specific: all three games' events run through the same `GameEventHandler` filter.

10. **`App.SelectGameMode` never offered a game's maximum player count — found and fixed 2026-07-26.** `Enumerable.Range(min, max - min)` treats the second argument as an end value when it is actually a *count*, so the option list stopped one short: Qwixx offered 2–4 while the prompt one line above read "With how many players do you want to play (2-5)?", and the same off-by-one hid 7-player Gesjaakt and 10-player Take-5!. Found while auditing what was left before calling Qwixx done; the advertised-but-rejected value is also a live trigger for #7's unbounded retry loop in any scripted run. Fixed with `+ 1` on the count. Pre-existing engine code, not introduced by Qwixx. Verified by playing an actual 5-player manual Qwixx game end to end, which was impossible before. Note there is still no automated coverage here at all — the whole `Presentation` layer is untested (see #6), which is exactly why a one-character bug in the menu survived this long.

Of the remaining ones, #1 and #7 are worth fixing on their own merits (both are real bugs with reproducible evidence — #7 in particular is a disk-filling footgun), and #9 is a small, self-contained ergonomics win rather than a bug fix; the rest are structural/DRY observations (or, per #8, a confirmed non-issue) worth revisiting if more games get added to this engine.
